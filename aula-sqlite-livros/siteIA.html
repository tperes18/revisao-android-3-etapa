01_persistencia.md

Dados que Nunca Saem do Aparelho

Nas aulas de Consumo de APIs, os dados vinham de um servidor: Retrofit, JSON, Coroutines para não travar a Main Thread. Hoje é o oposto — nenhum byte entra ou sai pela internet. Tudo vive dentro de um banco SQLite, criado por vocês mesmos, com código.

Isso não é um passo atrás. Apps de agenda, notas, listas de tarefas e catálogos pessoais funcionam assim: o dado é do aparelho, ponto final. E entender como o SQLite funciona por baixo é o que faz uma biblioteca como o Room (que vocês vão encontrar mais pra frente) deixar de parecer mágica.

O que muda na arquitetura

O Repository continua cumprindo o mesmo papel de sempre: isolar o ViewModel de saber como os dados são guardados. A diferença é que, hoje, não existe nenhuma biblioteca fazendo esse trabalho por vocês — o Repository fala diretamente com o SQLiteOpenHelper.

Por que isso importa: o Room (que existe como biblioteca pronta) faz exatamente o que vamos fazer hoje à mão — só que gerado automaticamente a partir de anotações. Depois de ver o "motor" por dentro, a abstração do Room vai fazer muito mais sentido.

As formas de guardar dados no Android

SQLite não é a única opção — e escolher errado é um problema comum. Cada mecanismo resolve um tipo de necessidade:

MecanismoPara que serveQuando não usar
SharedPreferences
(e o mais moderno DataStore)		 Guardar poucos valores simples: se o modo escuro está ligado, o nome do último usuário, um contador. Não serve para listas ou registros relacionados — não há como fazer buscas ou ordenação.
Arquivos
(texto, JSON, imagens)		 Conteúdo grande e único: uma foto, um PDF baixado, um arquivo de log. Consultar "todos os livros de 1899" exigiria abrir e percorrer o arquivo inteiro na mão.
SQLite
(banco relacional)		 Muitos registros estruturados, com busca, filtro, ordenação e relações entre tabelas. Exagero para guardar uma única preferência de usuário.

Nossa Biblioteca guarda vários livros, com título, autor e ano — e vai precisar listá-los ordenados. É exatamente o caso de uso do SQLite.

Por que o SQLite está em toda parte

O SQLite não é uma tecnologia específica do Android: é um banco de dados que roda dentro do próprio aplicativo, sem servidor separado, e está embarcado em praticamente todo sistema moderno — navegadores, sistemas operacionais de celular e desktop, e uma enorme variedade de aplicativos. É provavelmente o banco de dados mais distribuído do mundo, justamente por ser leve e não exigir instalação.

No Android, ele vem incluído no próprio sistema: por isso esta aula não adiciona nenhuma dependência nova ao projeto. As classes que vamos usar já estão disponíveis desde a primeira versão do Android.

Consequência prática disso: o que você aprender hoje sobre tabelas, INSERT e SELECT não vale só para Android. É o mesmo SQL usado em back-end, em análise de dados e em qualquer banco relacional — é um conhecimento que atravessa a carreira inteira, não uma técnica isolada de uma plataforma.

Por que aprender o modo manual antes do Room

Existe um caminho mais curto: usar o Room desde o começo e nunca escrever SQL. Muitos tutoriais fazem isso. O problema aparece quando algo dá errado — e sempre dá.

  • Quando o Room lançar um erro de migração de schema, você precisa entender que existe uma tabela com estrutura fixa por trás.
  • Quando uma consulta ficar lenta, a solução envolve entender índices e o SQL gerado — não a anotação.
  • Quando precisar de uma consulta complexa, o Room vai pedir que você escreva o SQL na mão dentro de uma anotação @Query.

Em outras palavras: o Room economiza digitação, mas não dispensa o entendimento. Fazer uma vez à mão é o que transforma o Room de "mágica que às vezes falha" em "ferramenta que eu sei o que está fazendo".

02_sqlite_nativo.kt

SQLiteOpenHelper: o Coração do Banco

O Android já inclui um motor SQLite completo — não é preciso adicionar nenhuma biblioteca. A classe SQLiteOpenHelper gerencia o ciclo de vida do banco: criação, versão e atualização de schema.

MétodoQuando é chamado
onCreate(db)Uma única vez — na primeira vez que o app roda e o arquivo do banco ainda não existe.
onUpgrade(db, old, new)Quando o número da versão do banco aumenta — usado para migrar o schema.

É dentro de onCreate() que vocês escrevem, à mão, o SQL que cria a tabela:

SQL 
CREATE TABLE livros (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    titulo TEXT NOT NULL,
    autor TEXT NOT NULL,
    ano INTEGER NOT NULL
)
Atenção com onUpgrade(): se vocês mudarem a tabela (adicionar uma coluna, por exemplo) e não aumentarem DATABASE_VERSION, o Android não vai chamar onUpgrade() — e o app vai continuar rodando com o schema antigo, gerando erros confusos de "coluna não existe".

O que acontece de fato quando o Android chama onCreate() e onUpgrade()

O arquivo do banco (biblioteca.db) fica salvo no armazenamento interno do celular, fora do controle direto do seu código — o SQLiteOpenHelper só entra em ação quando alguém pede writableDatabase ou readableDatabase pela primeira vez. Nesse momento, ele checa duas coisas:

  • O arquivo do banco já existe? Se não — primeira instalação do app — ele cria o arquivo do zero e chama onCreate().
  • A versão salva no arquivo é menor que DATABASE_VERSION? Se sim — o app foi atualizado desde a última vez que rodou — ele chama onUpgrade() com a versão antiga e a nova.

Se nenhuma das duas condições for verdadeira (o banco já existe e a versão não mudou), nenhum dos dois métodos é chamado — o Android simplesmente abre o banco que já está lá. É por isso que só mudar o código do onCreate() não tem efeito nenhum num celular que já instalou o app antes: aquele método só roda uma vez, na criação.

Repository sem Mágica

Sem um ORM (como o Room), o Repository precisa fazer manualmente duas coisas que uma biblioteca normalmente faria por vocês: montar os dados para gravar, e reconstruir os objetos Kotlin a partir do que volta do banco.

Duas peças que vocês vão escrever à mão

  • ContentValues: um mapa chave-valor que representa uma linha a ser inserida — o equivalente manual do que uma anotação @Insert faria sozinha.
  • Cursor: um "ponteiro" que percorre linha por linha do resultado de uma query — precisa ser percorrido com moveToNext() e fechado depois de usado (ou usando a função use { } do Kotlin, que fecha automaticamente).
Reaproveitando o que já foi ensinado: acesso a disco também é uma operação bloqueante. A mesma regra da aula de APIs se aplica — nada de Cursor ou ContentValues na Main Thread. O Repository continua usando suspend fun e Dispatchers.IO.

database/DatabaseHelper.kt 
package com.seunome.biblioteca.database

import android.content.Context
import android.database.sqlite.SQLiteDatabase
import android.database.sqlite.SQLiteOpenHelper

class DatabaseHelper(context: Context) :
    SQLiteOpenHelper(context, DATABASE_NAME, null, DATABASE_VERSION) {

    override fun onCreate(db: SQLiteDatabase) {
        db.execSQL(
            """
            CREATE TABLE $TABLE_LIVROS (
                $COL_ID INTEGER PRIMARY KEY AUTOINCREMENT,
                $COL_TITULO TEXT NOT NULL,
                $COL_AUTOR TEXT NOT NULL,
                $COL_ANO INTEGER NOT NULL
            )
            """.trimIndent()
        )
    }

    override fun onUpgrade(db: SQLiteDatabase, oldVersion: Int, newVersion: Int) {
        db.execSQL("DROP TABLE IF EXISTS $TABLE_LIVROS")
        onCreate(db)
    }

    companion object {
        const val DATABASE_NAME = "biblioteca.db"
        const val DATABASE_VERSION = 1
        const val TABLE_LIVROS = "livros"
        const val COL_ID = "id"
        const val COL_TITULO = "titulo"
        const val COL_AUTOR = "autor"
        const val COL_ANO = "ano"
    }
}

Passo 3 — Repository: Gravando com ContentValues 3 de 7

Local: pacote repository  |  Arquivo: LivroRepository.kt

repository/LivroRepository.kt (parte 1) 
package com.seunome.biblioteca.repository

import android.content.ContentValues
import com.seunome.biblioteca.database.DatabaseHelper
import com.seunome.biblioteca.model.Livro
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.withContext

class LivroRepository(private val dbHelper: DatabaseHelper) {

    suspend fun inserir(livro: Livro) = withContext(Dispatchers.IO) {
        val db = dbHelper.writableDatabase
        val valores = ContentValues().apply {
            put(DatabaseHelper.COL_TITULO, livro.titulo)
            put(DatabaseHelper.COL_AUTOR, livro.autor)
            put(DatabaseHelper.COL_ANO, livro.ano)
        }
        db.insert(DatabaseHelper.TABLE_LIVROS, null, valores)
    }
}
Repare: ContentValues é literalmente um mapa de "nome da coluna" para "valor" — é o que substitui a anotação @Insert do Room.
O que db.insert() gera por baixo dos panos: essa única linha de Kotlin equivale a rodar o seguinte SQL diretamente no banco: 
INSERT INTO livros (titulo, autor, ano)
VALUES ('Dom Casmurro', 'Machado de Assis', 1899);
Ver essa tradução ajuda a entender que ContentValues não é uma tecnologia nova — é só uma forma de montar esse INSERT sem concatenar strings SQL na mão (o que abriria brecha pra bugs e pra injeção de SQL).

Passo 4 — Repository: Lendo com Cursor 4 de 7

Local: pacote repository  |  Arquivo: LivroRepository.kt (continuação)

repository/LivroRepository.kt (parte 2) 
    suspend fun listarTodos(): List<Livro> = withContext(Dispatchers.IO) {
        val db = dbHelper.readableDatabase
        val cursor = db.query(
            DatabaseHelper.TABLE_LIVROS,
            null, null, null, null, null,
            "${DatabaseHelper.COL_ANO} DESC"
        )
        val livros = mutableListOf<Livro>()
        cursor.use {
            while (it.moveToNext()) {
                livros.add(
                    Livro(
                        id = it.getLong(it.getColumnIndexOrThrow(DatabaseHelper.COL_ID)),
                        titulo = it.getString(it.getColumnIndexOrThrow(DatabaseHelper.COL_TITULO)),
                        autor = it.getString(it.getColumnIndexOrThrow(DatabaseHelper.COL_AUTOR)),
                        ano = it.getInt(it.getColumnIndexOrThrow(DatabaseHelper.COL_ANO))
                    )
                )
            }
        }
        livros
    }
O SQL equivalente a esse db.query(): 
SELECT * FROM livros ORDER BY ano DESC;
E o Cursor devolvido é como uma "planilha" que o Android entrega linha por linha — moveToNext() anda uma linha pra frente, e getString/getInt leem uma célula daquela linha. É exatamente esse "andar linha por linha e montar um objeto" que o Room automatiza quando ele devolve uma List<Entity> pronta.
cursor.use { }: essa função do Kotlin fecha o Cursor automaticamente ao final do bloco, mesmo se der exceção — o equivalente a um "try-finally" que fecha o recurso sozinho.
Onde a maioria se perde neste passo: os null, null, null, null, null antes do "${DatabaseHelper.COL_ANO} DESC" não são erro de digitação — são parâmetros que o query() exige nessa ordem (colunas, filtro, argumentos do filtro, agrupamento, filtro de grupo) e que não estamos usando hoje. Se o app crashar com "coluna não encontrada", o primeiro lugar a olhar é se o nome usado em getColumnIndexOrThrow(...) é idêntico ao definido em DatabaseHelper — maiúsculas/minúsculas incluídas.

viewmodel/BibliotecaViewModel.kt 
package com.seunome.biblioteca.viewmodel

import android.app.Application
import androidx.compose.runtime.getValue
import androidx.compose.runtime.mutableStateOf
import androidx.compose.runtime.setValue
import androidx.lifecycle.AndroidViewModel
import androidx.lifecycle.viewModelScope
import com.seunome.biblioteca.database.DatabaseHelper
import com.seunome.biblioteca.model.Livro
import com.seunome.biblioteca.repository.LivroRepository
import kotlinx.coroutines.launch

sealed interface BibliotecaUiState {
    object Loading : BibliotecaUiState
    data class Success(val livros: List<Livro>) : BibliotecaUiState
    data class Error(val message: String) : BibliotecaUiState
}

class BibliotecaViewModel(application: Application) : AndroidViewModel(application) {

    private val repository = LivroRepository(DatabaseHelper(application))

    var uiState: BibliotecaUiState by mutableStateOf(BibliotecaUiState.Loading)
        private set

    init { carregarLivros() }

    fun carregarLivros() {
        viewModelScope.launch {
            uiState = BibliotecaUiState.Loading
            uiState = try {
                BibliotecaUiState.Success(repository.listarTodos())
            } catch (e: Exception) {
                BibliotecaUiState.Error(e.message ?: "Erro ao acessar o banco de dados.")
            }
        }
    }

    fun salvarLivro(titulo: String, autor: String, ano: Int) {
        viewModelScope.launch {
            repository.inserir(Livro(titulo = titulo, autor = autor, ano = ano))
            carregarLivros()
        }
    }
}
Por que AndroidViewModel? O DatabaseHelper precisa de um Context para existir — AndroidViewModel recebe a Application automaticamente, sem precisar de uma Factory manual.

package com.seunome.biblioteca.ui

import androidx.compose.foundation.layout.*
import androidx.compose.foundation.lazy.LazyColumn
import androidx.compose.foundation.lazy.items
import androidx.compose.material3.*
import androidx.compose.runtime.*
import androidx.compose.ui.Modifier

@Composable
fun BibliotecaScreen(viewModel: BibliotecaViewModel = viewModel()) {
    var titulo by remember { mutableStateOf("") }
    var autor by remember { mutableStateOf("") }
    var ano by remember { mutableStateOf("") }

    Column(modifier = Modifier.fillMaxSize().padding(16.dp)) {
        OutlinedTextField(value = titulo, onValueChange = { titulo = it }, label = { Text("Título") }, modifier = Modifier.fillMaxWidth())
        Spacer(Modifier.height(8.dp))
        OutlinedTextField(value = autor, onValueChange = { autor = it }, label = { Text("Autor") }, modifier = Modifier.fillMaxWidth())
        Spacer(Modifier.height(8.dp))
        OutlinedTextField(value = ano, onValueChange = { ano = it }, label = { Text("Ano") }, modifier = Modifier.fillMaxWidth())

        Button(
            onClick = {
                val anoInt = ano.toIntOrNull() ?: return@Button
                viewModel.salvarLivro(titulo, autor, anoInt)
                titulo = ""; autor = ""; ano = ""
            },
            modifier = Modifier.padding(top = 12.dp)
        ) { Text("Salvar Livro") }

        Spacer(modifier = Modifier.height(16.dp))

        when (val state = viewModel.uiState) {
            is BibliotecaUiState.Loading -> CircularProgressIndicator()
            is BibliotecaUiState.Error -> Text("Erro: ${state.message}")
            is BibliotecaUiState.Success -> LazyColumn {
                items(state.livros, key = { it.id }) { livro ->
                    ListItem(
                        headlineContent = { Text(livro.titulo) },
                        supportingContent = { Text("${livro.autor} · ${livro.ano}") }
                    )
                }
            }
        }
    }
}

06_troubleshooting.md

Erros Comuns e Como Resolver

Se algo der errado, procure aqui antes de recomeçar o projeto do zero.

requires libraries and applications that depend on it to compile against version 36 (ou 37) or later

O que significa: alguma biblioteca do projeto é mais nova que o compileSdk configurado e exige um SDK que provavelmente nem está instalado na máquina.

Solução: confira se o gradle/libs.versions.toml está exatamente como no Passo 0. A causa quase sempre é uma versão mais nova que a fixada — normalmente coreKtx, activityCompose ou lifecycleRuntimeKtx.

Se o erro voltar depois de corrigido, procure entradas duplicadas no arquivo (por exemplo, um coreKtxVersion além do coreKtx). Elas costumam ser deixadas pelo "AGP Upgrade Assistant" — dispense essa notificação quando ela aparecer.

Configuration contains AndroidX dependencies, but the android.useAndroidX property is not enabled

Solução: abra o arquivo gradle.properties (raiz do projeto, junto do settings.gradle.kts) e adicione a linha android.useAndroidX=true. Depois clique em Sync Now.

no such table: livros (ou no such column)

Causa: o método onCreate() só roda uma vez, quando o arquivo do banco é criado pela primeira vez. Se você mudou o SQL do CREATE TABLE depois de já ter rodado o app, o banco no aparelho continua com a estrutura antiga.

Solução rápida (em desenvolvimento): desinstale o app do emulador e rode de novo — isso apaga o banco e força o onCreate() a rodar outra vez.

Solução correta: aumente o número em DATABASE_VERSION. Isso faz o Android chamar o onUpgrade(), que no nosso código apaga e recria a tabela.

CursorIndexOutOfBoundsException ou "column ... does not exist"

Causa: o nome de coluna usado em getColumnIndexOrThrow(...) não bate exatamente com o nome definido no CREATE TABLE. A comparação diferencia maiúsculas e minúsculas.

Solução: por isso declaramos os nomes como constantes (COL_TITULO, COL_AUTOR...) no companion object — use sempre a constante, nunca o texto digitado à mão. Assim o compilador avisa se houver erro de digitação.

O app trava por alguns segundos ao salvar ou listar

Causa: a operação de banco está rodando na Main Thread.

Solução: confirme que todas as funções do Repository são suspend e que o corpo delas está dentro de withContext(Dispatchers.IO) { ... }. Acesso a disco é bloqueante, exatamente como acesso a rede.

Salvo um livro, mas ele não aparece na lista

Causa: diferente do Room, o SQLite manual não avisa ninguém quando os dados mudam. A lista só é atualizada se alguém pedir de novo.

Solução: confirme que salvarLivro() chama carregarLivros() logo depois de inserir. É essa chamada que reconsulta o banco e atualiza o estado da tela.

Guarde essa limitação: ela é justamente um dos problemas que o Room resolve automaticamente com Flow, na próxima aula.

Unresolved reference (arquivo criado na pasta errada)

Causa: o painel do Android Studio agrupa pastas que contêm apenas uma subpasta, o que facilita criar um arquivo dentro de ui/theme por engano.

Solução: arraste o arquivo para a pasta correta e clique em Refactor quando o Android Studio perguntar sobre o package. Confirme depois que a primeira linha do arquivo corresponde à pasta onde ele está.

Quero ver o banco por dentro para conferir se salvou

Não é um erro, mas é a ferramenta que mais ajuda a diagnosticar. Com o app rodando, abra View > Tool Windows > App Inspection > Database Inspector. Você verá o arquivo biblioteca.db, a tabela livros e o conteúdo real de cada linha — inclusive em tempo real, conforme você insere dados pelo app.
